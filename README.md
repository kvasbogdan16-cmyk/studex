# Studex

Лендинг платформи, де студенти шукають першу роботу, підробіток або волонтерство.

**Сайт:** https://studex-ochre.vercel.app
**Адмін-панель:** https://studex-ochre.vercel.app/admin

## Як це працює

- **Форма заявки** (`index.html`, `script.js`) надсилає дані на `/api/lead`.
- **`api/lead.js`** (функція Vercel) зберігає заявку в Supabase і надсилає сповіщення в Telegram.
- **Адмін-панель** (`admin.html`, `admin.js`) після входу показує заявки (нові зверху), дає змінити статус і відфільтрувати за статусом. Налаштування Supabase бере з `/api/config`.
- **База даних**: таблиця `leads` зі статусами «нова», «в роботі», «закрита» (`supabase.sql`) і доступ лише для адмінів (`supabase-admin.sql`).
- **CRM** (`supabase-crm.sql`, запускати третім): етапи воронки, джерело заявки («Сайт» / «Вручну») та історія переходів між етапами, яку записує сама база.
- **Розпізнавання візиток** (`supabase-scan.sql`, запускати четвертим; `api/scan.js`): фото або PDF візитки йде в Claude API, адмін перевіряє поля, клієнт потрапляє у воронку з джерелом «Візитка», оригінал зберігається в закритому сховищі Supabase. Потрібна змінна `ANTHROPIC_API_KEY` у Vercel.
- **Telegram Mini App** (`supabase-telegram.sql`, запускати п'ятим; `tg.html`, `api/tg-*.js`): кнопка «Вакансії» в боті відкриває каталог, заявка потрапляє в CRM з джерелом «Telegram» і ім'ям з Telegram, у «Моїх заявках» видно етап. Сервер перевіряє підпис Telegram (initData) ключем бота і звертається до бази через секрет `TG_SERVER_SECRET` (у базі зберігається лише його SHA-256). Кнопку меню бота налаштовує `POST /api/tg-setup`.
- **Картинки для вакансій** (`supabase-images.sql`, запускати шостим; `api/generate.js`): в адмінці розділ «Картинки» — опис → GPT Image (`gpt-image-2.5-flare`) на сервері → картинка в закритому сховищі Supabase й історії генерацій. Ліміт 5 на день на адміна (перевіряє база), невдалі спроби не рахуються. Потрібна змінна `OPENAI_API_KEY` у Vercel.
- **Чат відмов** (`supabase-refusals.sql`, запускати сьомим; `api/refusals-*.js`): окремий бот у Telegram-групі. Менеджери пишуть відмову за шаблоном (`Місто:`, `Причина:`, за бажанням `Ім'я:`, `Телефон:` і `Коментар:`; місто можна вказати хештегом `#Львів`), бот зберігає її й ставить 👍. Телефон зводиться до вигляду `+380671234567`; якщо в ньому не 10–13 цифр, бот просить виправити. Редагування повідомлення оновлює відмову, `/undo` у відповідь на неї прибирає її зі звітів, `/help` показує шаблон.
  - **Звіт на вимогу:** `/report` — бот показує кнопки з містами (ті, де були відмови за 90 днів, і «Усі міста»), потім з періодом: цей / минулий тиждень, цей / минулий місяць. Для «Усі міста» приходить загальний звіт, для міста — детальний. `/report Київ` одразу пропускає вибір міста. Поточний тиждень чи місяць рахується «станом на сьогодні» й порівнюється з тими ж днями попереднього.
  - **Автоматичні звіти:** Vercel Cron щодня о 07:00 UTC запускає `/api/refusals-report`. У понеділок у чат приходять звіти за минулий тиждень (пн–нд), 1-го числа — за минулий місяць, в інші дні нічого. Кожен раз — загальний звіт і детальний по Львову. Межі періодів — за київським часом.
  - **Загальний звіт:** кількість і динаміка до попереднього періоду, розбивка по містах і топ причин. **Детальний по місту:** причини, розбивка по днях (тиждень) або тижнях (місяць), хто вносив і список усіх відмов з ім'ям, телефоном і посиланням на повідомлення.
- **Ліміт заявок із сайту** (`supabase-ratelimit.sql`, запускати восьмим): 3 заявки на добу з одного номера і 60 на годину загалом. Перевіряє база (тригер), тож ліміт діє і для запису напряму в Supabase. При перевищенні `/api/lead` відповідає 429 і не надсилає сповіщення. Перевірка в живій базі — `tests/sql/ratelimit.sql` у SQL Editor.
- **2FA для адмінки** (`supabase-mfa.sql`, запускати дев'ятим, лише після підключення 2FA всіма адмінами; `admin-mfa.js`): після пароля адмінка просить 6-значний код із застосунку Authenticator (уперше — QR-код і секрет, який треба зберегти в менеджері паролів). База (`is_admin()`) довіряє лише сесії aal2, тож пароль без коду не дає нічого: ні через сайт, ні через REST Supabase, ні через `/api/*`. Запобіжник у SQL відмовляється запускатися, якщо в когось з адмінів немає підтвердженого 2FA. Перевірка в живій базі — `tests/sql/mfa.sql` у SQL Editor. Порядок викатки, відновлення і відкат — у розділі «2FA для адмінки» нижче.

### Як підключити чат відмов

1. У @BotFather створи нового бота, а його токен збережи у Vercel як `REFUSALS_BOT_TOKEN`.
2. Додай бота в групу й зроби його адміном. Без цього він бачить лише команди, а не звичайні повідомлення. Інший варіант: вимкни Group Privacy в @BotFather і додай бота заново.
3. Запусти `supabase-refusals.sql` у Supabase. Скрипт можна запускати повторно: якщо таблиця вже є, він додасть нове (поле телефону, звіти за період).
4. Задай у Vercel `CRON_SECRET` (будь-який довгий випадковий рядок) і задеплой.
5. Підключи вебхук: `curl -X POST https://studex-ochre.vercel.app/api/refusals-setup -H "X-Setup-Secret: <TG_SERVER_SECRET>"` (або з `-H "Authorization: Bearer <CRON_SECRET>"`). Якщо бот уже був підключений раніше, виконай це ще раз — інакше кнопки `/report` не працюватимуть (вебхук має приймати натискання кнопок).
6. Напиши `/help` у групі. Бот покаже ID чату: збережи його у Vercel як `REFUSALS_CHAT_ID` і задеплой ще раз. Якщо групу колись перетворять на супергрупу, ID зміниться, і його треба буде оновити.
7. Щоб перевірити автоматичний звіт, не чекаючи понеділка чи 1-го числа (з тим самим заголовком `-H "Authorization: Bearer <CRON_SECRET>"`):
   - `https://studex-ochre.vercel.app/api/refusals-report?month=2026-11` — за місяць;
   - `…/api/refusals-report?week=2026-11-16` — за тиждень, у який входить ця дата;
   - додай `&dry=1`, щоб лише побачити текст у відповіді, нічого не надсилаючи в чат.

### 2FA для адмінки

1. **Порядок викатки** (щоб не заблокувати себе): екран 2FA на продакшні → кожен адмін входить і підключає 2FA → лише тоді `supabase-mfa.sql` → одразу `tests/sql/mfa.sql`. Не виходь з адмінки, доки тест не покаже «✅ усі перевірки пройдено».
2. **Втрата телефона** (кроки строго по порядку; повний текст — наприкінці `supabase-mfa.sql`):
   1. Змінити пароль адміна: Dashboard → Authentication → Users (унікальний, довгий, у менеджері паролів).
   2. Завершити всі сесії адміна («Sign out user» у Dashboard або `delete from auth.sessions` в SQL Editor).
   3. Видалити MFA-фактор (Dashboard або `delete from auth.mfa_factors`), для певності через годину після кроку 2, коли старий access-токен прострочився.
   4. Увійти новим паролем і підключити новий фактор (адмінка покаже QR-код), секрет зберегти в менеджері паролів.
3. **Новий адмін** (кроки строго по порядку; повний текст — наприкінці `supabase-mfa.sql`):
   1. Створити користувача: Dashboard → Authentication → Users → Invite user.
   2. Він приймає запрошення, задає пароль, входить в адмінку й сам підключає 2FA (після коду адмінка скаже, що доступу немає, — так і має бути).
   3. Перевірити в SQL Editor, що в нього рівно один фактор `totp` / `verified`, створений щойно (`auth.mfa_factors`).
   4. Лише тепер додати його email у нижньому регістрі: `insert into public.admins (email) values (...)`.

   Чому так: доки в акаунта немає підтвердженого фактора, будь-хто з його паролем може підключити свій. Якщо email уже в списку адмінів, перший, хто дізнався пароль, отримає повний доступ до CRM.
4. **Відкат:** спершу блок відкату з `supabase-mfa.sql` в SQL Editor, потім (за потреби) фронтенд через Vercel → Instant Rollback. Старий `admin.js` без екрана 2FA входить лише паролем (aal1), тож якщо відкотити фронтенд першим, а `is_admin()` ще вимагає aal2, стара адмінка викине тебе. Після відкату база знову відкрита лише за паролем: поверни `supabase-mfa.sql`, щойно усунеш причину.
5. **Пароль адміна:** унікальний, довгий, у менеджері паролів. 2FA — другий бар'єр, а не єдиний: Supabase обмежує спроби коду до 15 на хвилину з одного IP (змінити не можна), але зловмисник з паролем і багатьма IP перебирає швидше. Невдалі спроби видно в Supabase → Authentication → Logs.

## Тести

`npm test` перевіряє синтаксис усіх JS-файлів і запускає `tests/*.test.js` через вбудований `node --test`, без залежностей.

## Ключі

У коді немає жодного ключа чи токена. Усі вони зберігаються у Vercel → Settings → Environment Variables:

| Змінна | Що це |
|---|---|
| `SUPABASE_URL` | адреса проєкту Supabase |
| `SUPABASE_PUBLISHABLE_KEY` | publishable-ключ Supabase |
| `TELEGRAM_BOT_TOKEN` | токен бота від @BotFather |
| `TELEGRAM_CHAT_ID` | чат, куди приходять сповіщення |
| `REFUSALS_BOT_TOKEN` | токен бота чату відмов |
| `REFUSALS_CHAT_ID` | ID групи відмов (бот покаже його на `/help`) |
| `CRON_SECRET` | секрет, з яким Vercel Cron запускає автоматичні звіти (щотижня й щомісяця) |

Шаблон є в `.env.example`.
